# 클러스터 관리

## 개요

클러스터는 여러 Liberty 서버를 하나의 논리적 그룹으로 묶어 관리하는 기능입니다. LibriX의 클러스터 관리를 통해 서버들을 통합하여 배포, 구성 변경, 모니터링을 일괄적으로 수행할 수 있습니다.

## 클러스터란?

클러스터는 동일한 애플리케이션을 실행하는 여러 Liberty 서버들의 논리적 그룹입니다. 클러스터의 모든 멤버 서버는 동일한 구성과 애플리케이션을 가지며, 로드 밸런서를 통해 트래픽을 분산받습니다.

### Liberty의 전통적인 클러스터 관리

Open Liberty는 기본적으로 클러스터 개념이 없습니다. WebSphere Liberty의 Collective Controller를 사용하거나, 수동으로 관리해야 합니다.

#### 수동 클러스터 관리

**전통적인 방식:**
```bash
# 각 서버마다 개별 작업
ssh server1 "cd /opt/liberty && bin/server start myServer"
ssh server2 "cd /opt/liberty && bin/server start myServer"
ssh server3 "cd /opt/liberty && bin/server start myServer"

# 애플리케이션 배포도 개별 수행
scp myapp.war server1:/opt/liberty/usr/servers/myServer/dropins/
scp myapp.war server2:/opt/liberty/usr/servers/myServer/dropins/
scp myapp.war server3:/opt/liberty/usr/servers/myServer/dropins/
```

**문제점:**
- 서버별 개별 작업 필요
- 일관성 유지 어려움
- 자동화 스크립트 필요
- 오류 발생 시 추적 어려움
- 중앙 모니터링 불가

#### WebSphere Liberty Collective

```bash
# Collective Controller 설정
bin/collective create controller --keystorePassword=password

# 멤버 서버 등록
bin/collective join member --host=controller.company.com \
                           --port=9443 \
                           --keystorePassword=password
```

**문제점:**
- 복잡한 초기 설정
- 인증서 관리 필요
- GUI가 제한적 (Admin Center)
- 학습 곡선 높음

### LibriX의 클러스터 방식

**GUI 기반 관리:**
- 드래그 앤 드롭으로 서버 추가
- 시각적 토폴로지 뷰
- 실시간 상태 모니터링

**중앙 집중 배포:**
- 클러스터 단위 일괄 배포
- 무중단 롤링 업데이트
- 자동 롤백 기능

**통합 모니터링:**
- 클러스터 전체 헬스 체크
- 멤버별 성능 비교
- 통합 로그 뷰

## 클러스터의 이점

### 고가용성 (High Availability)

**서버 장애 대응:**
- 한 서버 장애 시 다른 서버가 처리
- 자동 페일오버
- 무중단 서비스

### 확장성 (Scalability)

**수평 확장:**
- 서버 추가로 처리 용량 증가
- 동적 스케일링
- 트래픽 분산

### 유지보수 편의성

**일괄 작업:**
- 클러스터 단위 배포
- 동시 설정 변경
- 통합 모니터링

## 클러스터 관리 화면

클러스터 관리 화면에 접근:

```
서버 → 클러스터
```

### 클러스터 목록

**표시 정보:**
- **클러스터 이름**: 고유 식별자
- **멤버 수**: 클러스터에 속한 서버 수
- **상태**: 모든 멤버 실행 중 / 일부 중지 / 모두 중지
- **애플리케이션**: 배포된 애플리케이션 수
- **설명**: 클러스터 용도

## 클러스터 생성

### 생성 절차

**1단계: 기본 정보**

- **클러스터 이름**: 영문, 숫자, 하이픈, 언더스코어
- **설명**: 클러스터 용도 (선택)

**예제:**
```
이름: web-app-cluster
설명: 웹 애플리케이션 클러스터 (운영 환경)
```

**2단계: 멤버 서버 선택**

클러스터에 추가할 Liberty 서버 선택:

**선택 기준:**
- 동일한 애플리케이션 실행 서버
- 비슷한 하드웨어 스펙
- 동일한 네트워크 세그먼트 (권장)

**멤버 추가 방법:**
- 개별 서버 선택
- 드래그 앤 드롭
- 서버 그룹 선택

**3단계: 클러스터 설정**

**세션 복제:**
```
☑ 세션 복제 활성화
세션 도메인: (기존 도메인 선택 또는 신규 생성)
```

**로드 밸런싱:**
```
로드 밸런서: (웹 서버 선택)
밸런싱 방식: Round Robin
세션 스티키: ☑
```

**4단계: 생성**

## 클러스터 멤버 관리

### 멤버 추가

**절차:**
1. 클러스터 선택
2. "멤버 추가" 버튼 클릭
3. 추가할 서버 선택
4. 확인

**자동 동기화:**
- 기존 애플리케이션 자동 배포
- 설정 동기화
- 세션 복제 구성

### 멤버 제거

**절차:**
1. 제거할 멤버 선택
2. "제거" 버튼 클릭
3. 확인

**안전한 제거:**
```
1. 로드 밸런서에서 제외 (Drain)
2. 기존 요청 완료 대기
3. 서버 중지
4. 클러스터에서 제거
```

### 멤버 상태

**상태 종류:**
- 🟢 **실행 중**: 정상 작동
- 🟡 **경고**: 성능 저하 또는 일부 문제
- 🔴 **중지**: 서버 미실행
- ⚪ **알 수 없음**: 통신 불가

## 클러스터 작업

### 시작/중지/재시작

**클러스터 시작:**
- 모든 멤버 서버 동시 시작
- 또는 순차적 시작

**클러스터 중지:**
```
○ 즉시 중지: 모든 서버 동시 중지
○ 순차 중지: 한 대씩 중지 (무중단)
```

**클러스터 재시작:**
```
○ 롤링 재시작: 한 대씩 순차 재시작 (권장)
○ 동시 재시작: 모든 서버 동시 재시작
```

### 애플리케이션 배포

**클러스터 단위 배포:**
1. 클러스터 선택
2. "애플리케이션 설치" 버튼
3. WAR/EAR 파일 업로드
4. 배포 옵션 선택
5. 배포 실행

**배포 전략:**

#### 동시 배포
```
모든 서버에 동시 배포
- 빠른 배포
- 짧은 서비스 중단 발생
```

#### 롤링 배포 (권장)
```
서버를 하나씩 순차 배포
- 무중단 배포
- 시간은 더 소요
- 문제 발생 시 쉬운 롤백
```

**롤링 배포 프로세스:**
```
1. Server1: 
   - 로드 밸런서에서 제외
   - 새 버전 배포
   - 헬스 체크
   - 로드 밸런서에 추가

2. Server2:
   - 로드 밸런서에서 제외
   - 새 버전 배포
   - 헬스 체크
   - 로드 밸런서에 추가

3. Server3:
   - (동일 반복)
```

#### Blue-Green 배포
```
1. Green (현재): 서비스 중
2. Blue (신규): 새 버전 배포 및 테스트
3. 전환: 로드 밸런서를 Blue로 전환
4. Green 제거 또는 대기
```

### 설정 변경

**클러스터 단위 설정:**
- JVM 옵션
- Liberty 변수
- 공유 라이브러리
- 가상호스트

**변경 적용:**
```
○ 즉시 적용 (재시작 없음)
○ 롤링 재시작 (순차 적용)
○ 수동 적용 (나중에 재시작)
```

## 로드 밸런싱 통합

### 웹 서버 연동

**자동 구성:**
클러스터 생성 시 웹 서버 자동 업데이트:

```apache
# Apache httpd.conf
<Proxy balancer://web-app-cluster>
    BalancerMember http://server1:9080 route=server1
    BalancerMember http://server2:9080 route=server2
    BalancerMember http://server3:9080 route=server3
    ProxySet lbmethod=byrequests
    ProxySet stickysession=JSESSIONID
</Proxy>

ProxyPass / balancer://web-app-cluster/
ProxyPassReverse / balancer://web-app-cluster/
```

### 헬스 체크

**자동 헬스 체크:**
```
엔드포인트: /health
간격: 30초
타임아웃: 5초
실패 임계값: 3회
```

**헬스 체크 실패 시:**
1. 로드 밸런서에서 자동 제외
2. 관리자에게 알림
3. 복구 후 자동 재추가

## 세션 복제

### 클러스터 세션 공유

**세션 도메인 자동 구성:**
클러스터 생성 시 세션 도메인 자동 생성:

```xml
<server>
    <!-- 세션 복제 설정 -->
    <httpSessionDatabase dataSourceRef="SessionDS"/>
    
    <dataSource id="SessionDS" jndiName="jdbc/sessions">
        <jdbcDriver libraryRef="PostgreSQL"/>
        <properties.postgresql
            serverName="session-db.company.com"
            portNumber="5432"
            databaseName="sessions"/>
    </dataSource>
</server>
```

**세션 페일오버:**
- Server1 장애 시
- Server2가 세션 인계
- 사용자는 끊김 없이 계속 서비스 이용

## 클러스터 모니터링

### 대시보드

LibriX는 클러스터 통합 대시보드 제공:

**전체 메트릭:**
- 총 처리량 (TPS)
- 평균 응답 시간
- 에러율
- 활성 세션 수

**멤버별 비교:**
```
Server1: CPU 45%, 메모리 2.5GB, TPS 150
Server2: CPU 50%, 메모리 2.8GB, TPS 180
Server3: CPU 40%, 메모리 2.3GB, TPS 120
```

**불균형 감지:**
- 특정 서버에 부하 집중
- 자동 알림
- 밸런싱 재조정 제안

### 알림 설정

**클러스터 수준 알림:**
- 50% 이상 멤버 중지
- 평균 응답 시간 > 3초
- 에러율 > 5%
- 세션 복제 실패

**멤버 수준 알림:**
- 개별 서버 중지
- CPU > 80%
- 메모리 > 90%
- 디스크 > 85%

## Liberty와 LibriX 비교

| 항목 | Open Liberty | Liberty Collective | LibriX 클러스터 |
|------|-------------|-------------------|---------------|
| 클러스터 개념 | 없음 | 있음 | 있음 |
| 초기 설정 | 수동 | 복잡 | 간단 (GUI) |
| 서버 추가 | 수동 | 수동 등록 | 드래그 앤 드롭 |
| 일괄 배포 | 불가 | 가능 | 가능 (롤링) |
| 무중단 배포 | 수동 구현 | 제한적 | 완전 지원 |
| 통합 모니터링 | 없음 | 기본 | 고급 대시보드 |

## 모범 사례

### 클러스터 크기

**권장 멤버 수:**
- 최소: 2대 (HA)
- 권장: 3~5대
- 최대: 10대 이하 (관리 편의성)

**대규모 환경:**
- 여러 클러스터로 분할
- 지역별 클러스터
- 서비스별 클러스터

### 서버 구성

**DO:**
- 동일한 하드웨어 스펙
- 동일한 Liberty 버전
- 동일한 JDK 버전
- 동일한 네트워크 대역폭

**DON'T:**
- 다양한 스펙 혼용
- 다른 버전 혼용
- 원격 데이터센터 혼합

### 배포 전략

**운영 환경:**
- 항상 롤링 배포 사용
- 충분한 헬스 체크 시간
- 자동 롤백 활성화

**개발/테스트 환경:**
- 동시 배포 가능
- 빠른 피드백 우선

## 클러스터 확장 시나리오

### 수평 확장 (Scale Out)

**트래픽 증가 대응:**
```
1. 새 서버 준비
2. Liberty 설치 및 구성
3. 클러스터에 추가
4. 자동으로 애플리케이션 배포
5. 로드 밸런서에 자동 추가
```

### 수직 확장 (Scale Up)

**개별 서버 성능 향상:**
```
1. 서버 선택
2. 로드 밸런서에서 제외 (Drain)
3. 서버 중지
4. 리소스 증가 (CPU, 메모리)
5. 서버 재시작
6. 로드 밸런서에 재추가
```

### 지역별 확장

**다중 리전 클러스터:**
```
리전1 클러스터: 3대
리전2 클러스터: 3대
글로벌 로드 밸런서: 지역별 라우팅
```

## 문제 해결

### 클러스터 일부 멤버 중지

**증상:** 일부 서버만 실행 중

**원인 및 해결:**

1. **서버 장애**
   - 서버 로그 확인
   - 재시작 시도
   - 필요 시 멤버 교체

2. **네트워크 문제**
   - 네트워크 연결 확인
   - 방화벽 규칙 확인

3. **리소스 부족**
   - CPU, 메모리 확인
   - 디스크 공간 확인

### 세션 복제 실패

**증상:** 서버 간 세션 공유 안 됨

**원인 및 해결:**

1. **데이터베이스 연결 실패**
   - 세션 DB 상태 확인
   - 연결 문자열 확인

2. **설정 불일치**
   - 모든 멤버 설정 확인
   - 세션 도메인 구성 확인

### 로드 불균형

**증상:** 특정 서버에 트래픽 집중

**원인 및 해결:**

1. **세션 스티키**
   - 세션 타임아웃 확인
   - 세션 분포 확인

2. **서버 성능 차이**
   - 가중치 조정
   - 느린 서버 교체

3. **로드 밸런서 설정**
   - 밸런싱 알고리즘 확인
   - 헬스 체크 확인

## 성능 최적화

### JVM 튜닝

**클러스터 단위 JVM 설정:**
```bash
-Xms2g -Xmx4g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:ParallelGCThreads=4
```

### 연결 풀 설정

**데이터소스 최적화:**
```
최소 연결: 10
최대 연결: 50
연결 타임아웃: 30초
```

**클러스터 전체 연결:**
```
3대 클러스터 × 최대 50 연결 = 150 연결
→ DB 최대 연결 수: 200 이상 권장
```

### 캐싱

**분산 캐시:**
- JCache 구현 (Ehcache, Infinispan)
- 클러스터 간 캐시 동기화
- 캐시 히트율 모니터링
